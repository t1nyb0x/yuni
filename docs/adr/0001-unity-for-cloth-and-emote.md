# ADR-0001: クロスとエモートのために Unity で作り直す

- 状態: **採用**（ただし PoC-1 の結果により覆りうる。「影響」節を参照）
- 決定日: 2026-08-30
- 関連: [moca ADR-0017](https://github.com/t1nyb0x/moca/blob/main/docs/adr/0017-vrm-pmx-only.md)、`../feasibility.md`、`../requirements.md`

---

## 文脈

moca v0.7.0 は感情に応じた姿勢表現（F-14）を実装したが、その過程で**手続き的なボーン操作の限界**に突き当たった。CHANGELOG に既知の制限として次が記録されている。

> モーションはボーンの回転による近似のため、大振りな動きは作成不可。座る・手を振るといった動作は範囲外

同時に moca ADR-0017 は、座り姿勢の実装を試みた結果として次を記録した。

> 膝関節を過度に曲げるとメッシュの融合が生じ、布系オブジェクトの物理演算が適切に機能しない

そして「布が正しく振る舞い、座ったり大きく動いたりする自然な挙動は目標に含めない」と決定した。**この決定は moca の枠内では正しい。** VRM SpringBone は「垂れて押しのけられるだけ」であり、コライダから押し戻される力を持たないため、衣装が脚を貫通することを防げない。

しかし利用者が求めているのは、まさにその範囲外に置かれたものだった。

### 問題は 1 つではない

「座ると服が貫通する」は、性質の異なる 4 つの問題が重なっている（`feasibility.md` 第 2 章）。

| # | 問題 | Unity 化で解けるか |
|---|---|---|
| P-1 | 大振りの動作そのものが作れない | ✅ モーションクリップで解ける |
| P-2 | ボーンのある衣装（スカート等）が脚を貫通する | ✅ クロスシミュレーション＋人体コライダ |
| P-3 | ボーンの無い衣装が、脚の変形に引きずられて貫通する | ⚠️ MeshCloth が要る。自動適用は自作 |
| P-4 | unitypackage 配布モデルをそのまま使えない | ✅ AssetBundle 経由 |

**P-1 だけであれば Unity 化は要らない。** three.js にもモーションクリップ再生の道はある。Unity 化を正当化するのは P-2 と P-3 であり、とくに **P-3 は three-vrm 系のスタックが原理的に持たない能力**である。

---

## 決定

**Yuni として、moca を Unity で作り直す。**

moca ADR-0017 が代替案「案 2: moca を Unity で再実装」として一度退けた選択肢を、**別プロダクトとして**採る。moca は Yuni が 1.0 に到達した時点で保守を終了する。

技術的な骨格は次のとおり（`feasibility.md` 第 3 章で検証済み）。

| 要素 | 手段 |
|---|---|
| VRM のランタイム読込 | UniVRM |
| クロス | MagicaCloth2 の Runtime Construction API（`SerializeData` + `BuildAndRun()`） |
| 透過マスコットウィンドウ | UniWindowController（MIT） |
| エモート | Humanoid Mecanim + モーションクリップ |
| LLM 通信 | `System.Net.Http.HttpClient`（`UnityWebRequest` は使わない） |

---

## 検討した代替案

### 案 A: moca の枠内で解く（three-vrm に留まる）

**却下。** VRM SpringBone にコライダを足しても、押し戻す力を持たない構造は変わらない。P-3 に至っては手が無い。moca ADR-0017 がこの結論に既に到達している。

### 案 B: Unity Editor 拡張によるオフライン変換ツールに留める

利用者の VRM を Unity で開き、衣装にコライダを仕込んで VRM として書き出す。moca 本体は無改造で済む。

**却下。** ただし**捨てていない。** PoC-1 が通らなかった場合の縮退先として残す（「影響」節）。却下の理由は、コライダを仕込んだところで VRM SpringBone の押し戻せない性質は変わらず、P-2 の解決度が低いこと。P-3 には届かない。

### 案 C: Rust コアと Unity 描画層をプロセス分離する

moca のチャット・LLM・永続化をそのまま使い、描画だけ Unity に差し替える。

**却下。** moca ADR-0017 が挙げた理由（プロセス間通信の追加契約、二製品の並行開発）に加え、Yuni では致命的な問題がある。**F-13 のマスコット表示は透過ウィンドウを要求する。** 透過した WebView と Unity の描画を 1 枚のウィンドウへ合成する必要が生じ、クリックスルーの判定も二重になる。得られるものに対して代償が大きすぎる。

### 案 D: 何もしない

**却下ではない。真剣な選択肢である。** moca は v0.7.0 まで到達し、実用に耐えている。座り姿勢を諦めれば追加コストはゼロである。

採らない理由は、それが**利用者の要望の中心だから**である。moca ADR-0017 の文脈節が記録するとおり、0.7 のあと「座り姿勢への対応」と「Unity パッケージ形式のモデル読み込み」の要望が相次いだ。

## 影響

### 払うもの

| 項目 | moca | Yuni |
|---|---|---|
| 配布サイズ | 約 15MB | 150〜300MB |
| 起動時間 | 3 秒以内 | 5 秒程度 |
| 3D 非表示時の消費 | ゼロ | ゼロにできない（要件 F-02-3 を緩和） |
| 必須ランタイム | WebView2 | 不要 |
| 貢献の敷居 | Node + Rust | **Unity Editor が必須。クロスを触るには MagicaCloth2 の購入も要る** |

加えて、UI 全体・LLM 3 アダプタ・永続化・資格情報・音声連携・マスコットウィンドウを再実装する。**これが moca ADR-0017 が「案 2」を退けた理由の中身であり、消えていない。**

### 構造的な後退

**API キーの防壁が弱くなる。** moca は Rust コアと WebView のプロセス境界により、API キーが描画側へ渡らないことを構造的に保証していた（moca F-11-3）。Yuni は単一プロセスであり、この防壁が存在しない。規約でしか守れなくなる（要件 F-11-5）。

### 助かるもの

moca は「依存の向きは常に内側（domain）へ向かう」「domain は three.js にも Tauri にも依存しない」という規律を守っている。**この規律のおかげで、感情タグパーサ・各モーションコントローラ・カナ→ビセーム写像は C# へ機械的に移せる。** 仕様書とテストケースがそのまま資産になる。

LLM アダプタも、外部インターフェース仕様（moca 要件 7.1〜7.4）と記録済み SSE フィクスチャが言語に依存しないため、設計判断をやり直す必要がない。

### この決定が覆る条件

**PoC-1 が通らなかった場合、この ADR は廃止する。**

PoC-1 は「ランタイム読込した任意の VRM へ MagicaCloth2 を自動適用し、座りモーションで貫通しないこと」を確かめる（`feasibility.md` 第 7 章）。これが通らなければ P-2 は解けず、Unity 化は moca に対する優位を持たない。**その場合、moca ADR-0017 の判断が正しかったことになる。** 縮退先は上記「案 B」である。

**結果は通っても通らなくても ADR として記録すること。**
