# ADR-0003: クロスは SPCR JointDynamics を既定とし、MagicaCloth2 は対応予定に置く

- 状態: **採用**（PoC-1 の結果により覆りうる。「影響」節）
- 決定日: 2026-08-30
- 関連: 要件定義書 F-17-6、NF-L-2、[ADR-0001](0001-unity-for-cloth-and-emote.md)、`../poc/poc-1.md`

---

## 文脈

[ADR-0001](0001-unity-for-cloth-and-emote.md) は Unity 化の根拠をクロスシミュレーションに置いた。ではどの実装を使うのか。

### きっかけ — 実モデルの調査

利用者が持ち込んだ Tokyo6 の配布モデル（`.unitypackage` 4 本）を解析したところ、次が分かった。

- プレハブが **MagicaCloth v1**（初代）で組まれている。`Magica Bone Cloth_Skirt` / `Magica Bone Cloth_Hair` / `Magica Capsule Collider (LegD_L / LegD_R)` など
- **スカートのコライダ指定は太もも 2 本のみ。** 作者が「スカートは太ももにだけ当てる」と決めている。**これは座り貫通への対処そのものである**
- シェーダは **lilToon**（MIT）。パッケージには含まれず外部依存
- パッケージ内に**シェーダもスクリプトも DLL も無い。** 外部依存は MagicaCloth v1 と lilToon の 2 つだけ

v1 で組まれていたことから「v1 を採用してはどうか」という案が出た。

### v1 は採れない

| # | 事実 |
|---|---|
| 1 | **v1 も有償アセットである。** 無償だったことはない |
| 2 | **販売・サポートが終了している。** 正規の入手経路が存在しない |
| 3 | Unity 6 対応が保証されない（対応表記は Unity 2019.4.31+ のまま） |
| 4 | v2 とは公式に非互換 |
| 5 | エディタで事前計算したデータ（`BoneClothData` 等）を持つ構造であり、**ランタイム構築ができない可能性が高い**。要件 F-17-1（利用者の操作なしにクロスを構成する）が成立しない |

1 と 2 だけで詰んでいる。**入手できないものを土台にはできない。**

なお、検索結果に現れる「Magica Cloth Free Download」の類は有償アセットの海賊版配布であり、選択肢ではない。

### v1 の設定は失われない

v1 を採らなくても、**v1 で組まれたモデルの価値は回収できる。** プレハブの YAML を直接読めば構成を取り出せることを実測で確認した（MagicaCloth を 1 本も所持しない状態で実施）。

```
clothTarget.rootList: 14 本         ← スカートのチェーン
teamData.colliderList: 2 個          ← 当てる相手（太もも 2 本）
Capsule (LegD_L/R): length 0.137, startRadius 0.057, endRadius 0.058
Capsule (Chest):    length 0.068, radius 0.1
Sphere  (Head) ×2:  radius 0.07 / 0.057
```

**「どのボーンを揺らし、どこに当てるか」という骨組みは、どのバックエンドへも移せる。** 移せないのはソルバ固有の詰め値（質量カーブ、`worldMoveInfluence` 等）だけで、それは見ながら合わせる作業になる。

## 決定

**`IClothBackend` の実装を 3 つとし、SPCR JointDynamics を既定とする。**

| 実装 | 状態 | 位置づけ |
|---|---|---|
| `SpcrClothBackend` | **1.0 の実装対象** | 既定。[SPCR JointDynamics](https://github.com/SPARK-inc/SPCRJointDynamics)（MIT）。**リポジトリに同梱する** |
| `MagicaClothBackend` | **対応予定。インターフェースのみ確定** | 任意。所持者が有効化する。品質と MeshCloth（P-3）が要るとき |
| `NullClothBackend` | 1.0 の実装対象 | 最終退避。UniVRM の SpringBone へ委譲 |

**MagicaCloth2 は「実装しないが、インターフェースは今の段階で確定させる」扱いとする。** これは moca が `SpeechSynthesizer` に対して採った手法と同じである（moca アーキテクチャ 2.3 節: 「MVP では実装しないが、`SpeakStyle` の型と `emotion_axes` の存在を今の段階で確定させておく」）。

### 抽象の切り方

**実装が 1 つしかない抽象は、間違った抽象になりやすい。** SPCR に寄りすぎた `IClothBackend` を作ると、MagicaCloth2 を後から入れるときに合わなくなる。次を守る。

- **`IClothBackend` は BoneCloth 相当（ボーン駆動）だけを表現する。** MeshCloth（頂点駆動）を同じインターフェースへ混ぜない。**SPCR に存在しない概念だからである**
- バックエンドに**能力照会を持たせる。** 呼び出し側が「このバックエンドは何ができるか」を問える形にし、`if (backend is MagicaCloth)` のような分岐を書かせない
- 入力は「チェーンのルートボーン群」と「コライダの形状・配置」という**ソルバ非依存の中間表現**とする。v1 プレハブから読み出した構成も、VRM SpringBone 定義も、この中間表現へ落としてからバックエンドへ渡す

## 検討した代替案

### 案 A: MagicaCloth2 を既定にする（0.4 版までの方針）

**却下。ただし僅差である。**

MagicaCloth2 には**公式のランタイム構築 API**（`SerializeData` + `BuildAndRun()`）があり、要件 F-17-1 の実現性が高い。SPCR にはこれが無い。**技術的な確実性では MagicaCloth2 が上回る。**

却下の理由は費用ではなく**配布と保守の構造**にある。有償アセットを既定にすると:

- Asset Store EULA によりリポジトリへコミットできない（NF-L-1）
- したがって**アセット未所持の状態ではクロスが一切動かない。** `NullClothBackend` へ退避するしかなく、clone した第三者が触れるのは「Yuni の存在理由が動いていない Yuni」になる
- CI もクロスの経路を検証できない

SPCR は MIT なので同梱でき、**誰が clone しても既定でクロスが動く。** この差は開発の進めやすさに直結する。

**$27.50 という価格は却下の理由ではない。** 安い。PoC-1 で SPCR が立たなければ、迷わずこちらへ切り替える（「影響」節）。

### 案 B: MagicaCloth v1 を採用する

**却下。** 上記「v1 は採れない」の 5 点。とくに入手不可能である点が決定的。

### 案 C: UnityChan SpringBone 2.0（MIT）

MIT で、VRM エコシステムでの採用実績もある。

**却下。** 揺れ物としては良いが、スカートと脚の衝突については「カプセルコライダが使えず大きな球で代用する」「距離拘束の調整不足で膝がスカートを貫通する」といった報告があり、**まさに Yuni が解こうとしている問題の解決度が低い。**

### 案 D: Unity 内蔵の Cloth コンポーネント

**却下。** 無償だが球・カプセルコライダのみで品質が低く、実質的に維持されていない。

## 影響

### 引き受けるリスク

**トレードオフが反転した。** 費用は消えたが、確実性が下がった。

| # | リスク | 対処 |
|---|---|---|
| 1 | **SPCR のランタイム構築が未文書。** README はエディタ操作前提 | **MIT でソースが読めるため、エディタ側の構築処理を実行時に呼べる形へ自前で持っていける。** これは有償の閉じたアセットには使えない手である。最終コミットで追加された `SPCRJointDynamicsHelper` を最初に読むこと |
| 2 | ~~**最終コミットが 2023-10。約 3 年更新が止まっている**~~ | **2026-08-30 実測により大幅に低下。** Unity 6000.0.82f1 で **SPCR v2.0.11 が無修正でコンパイル成功**（エラー 0 / 非推奨警告 4）。警告はすべて `FindObjectOfType` 系の API 非推奨であり、動作には影響しない。**API 不整合による破綻は起きていない。** 更新停止＝Unity 6 で動かない、ではなかった |
| 3 | 品質が MagicaCloth2 に劣る可能性 | PoC-1 の判定基準（VRM 3 体以上で貫通しない）で測る。**主観で「まあ動く」と言わないこと** |
| 4 | MeshCloth 相当が無い | P-3（ボーン無し衣装）は解けない。**元々 1.0 の条件外**（要件 F-17-10）。変更なし |

### 実測で判明した落とし穴（2026-08-30）

**SPCR の `package.json` は `com.unity.burst` への依存を宣言していない。** しかし Runtime は Burst を使っており、Burst 未導入のプロジェクトへ入れると `CS0234: 'Unity.Burst' 名前空間が見つからない` が大量に出る。作者の開発プロジェクト側の `manifest.json` には `com.unity.burst` が入っているため、作者の手元では顕在化しない類の漏れである。

**対処**: 利用側で `com.unity.burst` を明示的に追加する（Unity 6000.0.82f1 の推奨は `1.8.30`）。**これは SPCR 側のバグであり、フォークするなら最初に直す項目になる**（U-14）。

### この決定が覆る条件

**PoC-1 で SPCR のランタイム構築が立たなければ、既定を MagicaCloth2 へ差し替える。** その場合も [ADR-0001](0001-unity-for-cloth-and-emote.md)（Unity 化そのもの）は覆らない。**バックエンドの選択と企画の成否は別の問題である。**

**PoC-1 にタイムボックスを切ること。** SPCR の実行時構築に見通しが立たない状態が続いたら、粘らずに MagicaCloth2 を買って先へ進む。$27.50 は、判断を遅らせる理由にならない。

### 副次的に良くなったこと

**NF-L-2 を強化できる。** 従来は「MagicaCloth2 を所持しない状態でビルドが通ること」だったが、**「有償アセットを 1 つも持たずにビルドが通り、かつクロスが動くこと」**へ引き上げる。CI がクロスの経路まで検証できるようになる。

**同梱物のライセンスが揃う。** SPCR（MIT）と lilToon（MIT）はいずれもリポジトリへコミットでき、配布物へ含められる。MagicaCloth2 だけが例外的な扱いになる。
