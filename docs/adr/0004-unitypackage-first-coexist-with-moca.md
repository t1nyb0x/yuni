# ADR-0004: Yuni の主目的を unitypackage 配布モデルに置き、moca と恒久的に共存する

- 状態: **採用**
- 決定日: 2026-08-31
- **[ADR-0001](0001-unity-for-cloth-and-emote.md) の一部を改訂する**（「moca の後継」「1.0 到達時に moca 保守終了」の 2 点）
- 関連: 要件定義書 1.1〜1.2 節、第 10 章

---

## 文脈

[ADR-0001](0001-unity-for-cloth-and-emote.md) は Yuni を **moca の完全な後継**と位置づけた。moca は Yuni が 1.0 に達した時点で保守を終了し、VRM 対応も含めて Yuni へ寄せる想定だった。要件定義書の「本書の読み方」も、1.0 到達時に moca の要件を全文取り込んで自立させる前提で書かれていた。

この前提が崩れた。

### きっかけ — 手元のモデルは VRM ではなかった

利用者が実際に使いたいモデルは Tokyo6 の `.unitypackage` 配布物であり、**VRM ではない。** 解析の結果、これらは FBX + lilToon マテリアル + MagicaCloth v1 のプレハブで構成されており、VRM SpringBone 定義を持たない（[ADR-0003](0003-spcr-as-default-cloth-backend.md)）。

そして利用者の判断は次のとおりである。

> yuni は unitypackage を主目的にする。VRM はおまけ。VRM 自体は moca でもいいわけだし

**これは正しい。** moca は v0.7.0 まで到達しており、VRM の表示・チャット・感情表現・音声・マスコット表示が実用に達している。**VRM を使いたいだけなら moca で足りる。** Yuni が VRM 対応で moca を置き換える理由は、実のところ薄い。

### 前提が崩れた結果

ADR-0001 が Unity 化を正当化した論拠は「P-2 / P-3（衣装の貫通）は three-vrm 系では原理的に解けない」だった。**この論拠自体は生きている。** 変わったのは*どの経路で解くか*である。

| | 旧 | 新 |
|---|---|---|
| 主経路 | 任意の VRM へ実行時にクロスを自動構成する | **作者が設定済みの unitypackage モデルを、その設定のまま動かす** |
| VRM | 主対象 | **おまけ。本命は moca** |
| moca | 1.0 到達時に保守終了 | **恒久的に共存** |

---

## 決定

### 1. Yuni の主目的は unitypackage 配布モデルである

優位（要件定義書 1.2 節）の順序を入れ替える。

| # | 優位 | 位置づけ |
|---|---|---|
| **A-3** | **unitypackage で配布されたモデルを、作者が設定したシェーダとクロスのまま使える** | **主。Yuni の存在理由** |
| A-1 | 衣装が脚・体と衝突し、座っても貫通しない | 主。ただし**主経路はモデルバンドル側**とする |
| A-2 | ボーン回転の近似では作れない動作を再生できる | 主 |

**VRM 経路（F-17 の自動クロス構成）は「おまけ」へ降格する。** 実装はするが、**1.0 の達成条件から外す。** VRM を使いたい利用者は moca を使えばよい。

### 2. moca と恒久的に共存する

**ADR-0001 の「1.0 到達時に moca を保守終了する」を撤回する。**

| 製品 | 対象 | 基盤 |
|---|---|---|
| **moca** | **VRM** | Tauri + React + three-vrm。軽量（約 15MB / 起動 3 秒） |
| **Yuni** | **unitypackage 配布モデル** | Unity。重い（150〜300MB / 起動 5 秒）が、シェーダとクロスがそのまま動く |

棲み分けが明確であり、二製品として成立する。

### 3. Yuni は moca 相当の機能を全部持つ

チャット・LLM 3 アダプタ・感情タグ・音声・マスコット表示まで Unity 側に持つ。**Yuni 単体で完結させる。**

moca が生き残るからといって Yuni を「表示専用ビューア」に絞ることはしない。Tokyo6 のモデルで moca と同じ体験が得られなければ、Yuni を使う意味が薄いためである。

### 4. 版番号を moca と対応させるのをやめる

要件定義書 D-2 は「バージョンの刻みを moca に合わせ、同じ番号が同じ機能水準を指すようにする」と定めていた。**これは後継関係を前提とした規則であり、共存する二製品には意味を持たない。** 撤回する。

代わりに **0.1 で Yuni の存在理由（A-3 / A-1 / A-2）を成立させる。** チャットの移植は 0.2 以降とする。理由は D-2 と同じ — **存在理由が動くことを最初に確かめる。**

## 検討した代替案

### 案 A: 当初どおり moca の後継とし、VRM も本命として追う

**却下。** VRM 対応で moca を置き換える実利が無い。moca は既に実用水準にあり、Yuni の VRM 対応が moca を上回るのは「クロスが効く」一点のみ。その一点のために、軽量な Tauri 製アプリを 300MB の Unity 製アプリで置き換えるのは割に合わない。

### 案 B: Yuni を表示専用ビューアに絞り、チャットは moca に任せる

移植コストが激減する魅力的な案であり、企画初期にも検討した（当時は「レンダラ専用サイドカー」として却下）。

**却下。** 二つのウィンドウを並べて使うことになり、「画面の向こうに相手がいる」という moca 由来の目的（要件定義書 1.1 節）が成立しない。Tokyo6 のモデルで会話ができないなら、Yuni は「よくできたモデルビューア」にとどまる。

### 案 C: 判断を保留し、1.0 到達時に moca を畳むか決める

**却下。** 二重管理の期間が読めなくなる。**明示的に共存を選ぶほうが、覚悟の量が正しく見積もれる。**

## 影響

### 引き受けるコスト — 二重管理

**要件定義書のリスク R-8（moca と Yuni の二重管理）が、回避すべきリスクから「意図して選んだコスト」に変わる。**

- 感情タグパーサ、各モーションコントローラ、カナ→ビセーム写像を **TypeScript と C# の二重で保守する**
- LLM 3 アダプタを Rust と C# の二重で保守する。プロバイダの仕様変更があれば両方直す
- `emotion-protocol.md` の変更は両方へ波及する

**軽減策**: 仕様の正は moca 側に置き続ける（要件定義書 0 章の「差分で書く」構造を維持する）。**Yuni 側で仕様を先に変えないこと。** 挙動が割れると、どちらが正しいのか誰にも分からなくなる。

### 文書構造への影響

要件定義書 0 章の「1.0 到達時に moca を保守終了し、その時点で本書へ全文を取り込んで自立させる」は**撤回する。** moca が生き続けるため、参照先が消えない。**差分で書く構造を恒久的に維持する。**

### VRM 経路の格下げ

- F-17 の自動クロス構成（VRM 向け）は**実装するが 1.0 の条件から外す**
- PoC のゲートが変わる。**PoC-1（VRM への自動構成）から PoC-2（モデルバンドル経路）へ移す**
- **これにより最大の技術リスク R-12（SPCR のランタイム構築が未文書）がクリティカルパスから外れる。** モデルバンドル経路では Unity Editor 上で SPCR を構成して焼き込むため、実行時構築を必要としない。SPCR が本来想定しているエディタ操作の範囲で済む

**この副次効果は大きい。** 主目的の変更が、たまたま最大の技術リスクを回避する形になっている。ただし**それを理由に主目的を決めたのではない**ことは記録しておく。順序が逆になると、技術的な都合で製品の目的を曲げることになる。

### 残る前提

[ADR-0001](0001-unity-for-cloth-and-emote.md) のうち次は**変わらない**。

- Unity 化の技術的論拠（P-2 / P-3 は three-vrm 系では解けない）
- 払うコストの見積り（配布サイズ、起動時間、UI 再実装、API キーの防壁が弱くなること）
- [ADR-0002](0002-unity-6000-0-lts.md)（Unity 6000.0 LTS 固定）、[ADR-0003](0003-spcr-as-default-cloth-backend.md)（SPCR 既定）
