# ADR-0005: クロスは常に Yuni が構成する。作者の設定は手がかりとして使う

- 状態: **採用**
- 決定日: 2026-08-31
- **[ADR-0004](0004-unitypackage-first-coexist-with-moca.md) の A-3 を改訂する**
- 関連: [ADR-0003](0003-spcr-as-default-cloth-backend.md)、要件定義書 1.2 節、F-17、F-18-7

---

## 文脈

[ADR-0004](0004-unitypackage-first-coexist-with-moca.md) は Yuni の主目的を **A-3「unitypackage で配布されたモデルを、作者が設定したシェーダとクロスのまま使える」**と定めた。

PoC-2 でこれを実装したところ、**クロスの部分が構造的に成立しないことが分かった。**

### unitypackage 配布モデルのクロスは統一されていない

| 方式 | 使われ方 | Yuni がそのまま動かせるか |
|---|---|---|
| MagicaCloth v1 | Tokyo6 がこれ。2023 年頃までの主流 | ❌ **販売終了で入手不可**（[ADR-0003](0003-spcr-as-default-cloth-backend.md)） |
| MagicaCloth2 | 現在の有償主流 | 購入すれば可能 |
| **VRChat PhysBone** | **BOOTH 配布アバターの大半** | ❌ **VRChat SDK 依存。外部で使えない** |
| DynamicBone | 旧世代だが現役のモデルも多い | 有償。別途購入 |
| VRM SpringBone | VRM 由来 | 可能 |
| 何も無い | 珍しくない | — |

**「作者が設定したまま動かす」には、作者が使ったランタイムを Yuni が積んでいる必要がある。全部は積めない。**

したがって A-3 のうち**クロスの部分は、特定方式で作られたモデルにしか適用できない。** 方式ごとに変換器を書き足していけば対応範囲は広がるが、**それは moca が PMX で撤退した構造そのものである**（moca ADR-0015 / R-12「モデルごとの手当てが際限なく必要になる」）。

### PoC-2 が示したこと

手元の 3 体だけでも分岐が発生した。

| モデル | スカートの実装 |
|---|---|
| Chifuyu | MagicaCloth v1 の **BoneCloth** |
| Karin | MagicaCloth v1 の **MeshCloth** |
| Rikka | MagicaCloth v1 の **MeshCloth** |

**同じ配布元・同じアセットでも方式が割れている。** SPCR は MeshCloth に相当する機能を持たないため、2/3 が変換できない。これを解くために MagicaCloth2（有償）の採用を検討したが、**MagicaCloth2 を入れても PhysBone や DynamicBone のモデルには何も効かない。** 一般化しない。

---

## 決定

**クロスは常に Yuni が自前で構成する。作者のクロス設定は「移植対象」ではなく「手がかり」として扱う。**

```
作者の設定（v1 / MagicaCloth2 / PhysBone / DynamicBone / 何も無い）
   │
   │  読めたら手がかりとして使う。読めなくても構わない
   │    ・どのボーンが衣装か
   │    ・どのコライダに当てるか
   │    ・粒子半径や重力の目安
   ▼
Yuni が構成する（常に同じバックエンド）
```

**必要なのは「衣装のボーンがあること」だけになる。** 方式に依存しない。

### A-3 を書き換える

| | 旧（ADR-0004） | 新 |
|---|---|---|
| A-3 | unitypackage 配布モデルを、**作者が設定したシェーダとクロスのまま**使える | unitypackage 配布モデルを、**作者のシェーダのまま**使え、**衣装が破綻しない** |

**シェーダは成立する。** lilToon で描画できることを PoC-2 の関門 A で実証した。**クロスは Yuni が構成する。**

## 検討した代替案

### 案 1: 作者のクロス設定を使い続ける（ADR-0004 の当初方針）

**却下。** 対応できるのは特定方式のモデルだけになり、方式ごとに変換器が増え続ける。moca が PMX で撤退した構造と同じ。

加えて、**変換すればするほど「作者が作ったまま」から遠ざかる**という自己矛盾がある。v1 → SPCR の変換で失われるもの（MeshCloth、質量カーブ、ソルバ固有の詰め値）は、変換の精度をいくら上げても戻らない。

### 案 2: MagicaCloth2 を採用して対応範囲を広げる

**却下。一般化しない。** MagicaCloth2 が効くのは「MagicaCloth2 で作られたモデル」と「v1 からの変換精度」だけであり、PhysBone や DynamicBone のモデルには何も効かない。$27.50 の問題ではなく、**方式の断片化という構造の問題である。**

### 案 3: 対応するクロス方式を明示して、それ以外は非対応とする

**却下。** 正直ではあるが、利用者が持っているモデルの方式を事前に判別できない。「動くかどうか買って試す」製品になる。

## 影響

### 単純になるもの

**バックエンドの選定問題が消える。** 常に BoneCloth で構成するため MeshCloth が要らない。[ADR-0003](0003-spcr-as-default-cloth-backend.md) が引き受けたリスク 4（SPCR に MeshCloth 相当が無い）は**無害化する。SPCR のままで足りる。** MagicaCloth2 は「対応予定」のまま据え置いてよい。

**VRM 経路とモデルバンドル経路が同じ実装になる。** 構成処理は共通で、違うのは手がかりの取得元だけである。

| 経路 | 手がかりの取得元 |
|---|---|
| モデルバンドル | プレハブ内の v1 / MC2 等の設定（読めれば） |
| VRM | SpringBone 定義 |
| どちらも読めない | Humanoid とボーン構造から推測（F-17-4） |

[ADR-0004](0004-unitypackage-first-coexist-with-moca.md) で「おまけ」に降格させた VRM 経路の自動構成（F-17-1〜4）は、**主経路の実装そのものになる。** PoC-1 の内容が本流へ戻る。

### 諦めるもの

**作者が調整した見た目の再現。** 布の柔らかさ、揺れ方、ソルバ固有の質感は Yuni のものになる。**作者の作品としての衣装の動きは失われる。**

これは小さくない代償である。ただし**代償を払わない道が存在しない**（上記「文脈」）。払うと決めたことを記録する。

### 判断の順序について

**この決定は「SPCR では 2/3 のモデルに対応できない」という PoC-2 の中間結果から導いた。** ただし当時の検証は脚を組んだ厳しい座り姿勢で行っており、**測り直しが必要な状態だった**（`../poc/poc-2.md` 2 節）。

**測り直しの結果に関わらず、この決定は変わらない。** 方式の断片化は測定条件と無関係だからである。順序として、技術的な行き詰まりが先に見えたことで構造の問題に気づいた形になっているが、**構造の問題のほうが先に存在していた。**
