## 0. 本書の読み方

Yuni は moca の後継である。**moca の要件をゼロから書き直さない。** 同じものを二度書けば必ず食い違い、どちらが正かが分からなくなる。

したがって本書は**差分で書く。**

- moca の要件をそのまま引き継ぐものは「継承」と記し、内容を再掲しない。正は [moca の要件定義書](https://github.com/t1nyb0x/moca/blob/main/docs/requirements.md)
- Unity 化によって**変わる**ものは、変更点だけを書く
- Yuni で**新しく増える**ものは、全文を書く
- moca から**落とす**ものは、落とす理由を書く

moca 側の文書が更新されたときに追随が要る。この構造の代償である。

**この構造は恒久的に維持する（D-7）。** 0.5 版までは「1.0 到達時に moca を保守終了し、その時点で本書へ全文を取り込んで自立させる」としていたが、[ADR-0004](adr/0004-unitypackage-first-coexist-with-moca.md) で撤回した。moca は VRM 用として生き続けるため、参照先が消えない。

**仕様の正は moca 側に置き続けること。Yuni 側で仕様を先に変えないこと。** 二製品の挙動が割れると、どちらが正しいのか誰にも分からなくなる。

## 1. 背景・目的とスコープ

### 1.1 目的

**unitypackage 形式で配布された 3D キャラクターモデルを、作者が設定したシェーダとクロスのまま動かし、そのキャラクターと対話できるようにする。**

moca と同じ体験 —「画面の向こうに相手がいる」— を、**作り込まれたモデルで、衣装が正しく振る舞う状態で**成立させる。

#### moca との棲み分け（D-6 / D-7）

| 製品 | 対象 | 基盤 | 性格 |
|---|---|---|---|
| **moca** | **VRM** | Tauri + React + three-vrm | 軽量（約 15MB / 起動 3 秒）。VRM ならこちらで足りる |
| **Yuni** | **unitypackage 配布モデル** | Unity | 重い（150〜300MB / 起動 5 秒）が、シェーダとクロスがそのまま動く |

**Yuni は moca の後継ではない。棲み分けの違う姉妹製品である。** 0.5 版までは「完全な後継。1.0 到達時に moca を保守終了」としていたが、[ADR-0004](adr/0004-unitypackage-first-coexist-with-moca.md) で撤回した。

理由は単純である。**VRM を使いたいだけなら moca で足りる。** moca は v0.7.0 で表示・チャット・感情表現・音声・マスコット表示が実用に達しており、Yuni の VRM 対応が moca を上回るのは「クロスが効く」一点のみ。その一点のために、軽量な Tauri 製アプリを 300MB の Unity 製アプリで置き換えるのは割に合わない。

moca は [ADR-0017](https://github.com/t1nyb0x/moca/blob/main/docs/adr/0017-vrm-pmx-only.md) で次を範囲外と決定した。

> マスコット的な振る舞い（布の正確なシミュレーション、複雑な座り姿勢）は moca の設計目標に含めません。

この決定は正しい。three.js と VRM SpringBone の組み合わせでは、揺れ物は「垂れて押しのけられるだけ」であり、布として掛ける仕組みを持たない。座り姿勢で膝を深く曲げればメッシュが融合し、衣装は脚を貫通する。**moca の枠内で解こうとしてはならない。**

Yuni はこの制約を外すために描画基盤を Unity へ移す。ADR-0017 が「案 2」として一度退けた選択肢を、**別プロダクトとして**採る。

### 1.2 Yuni が moca に対して持つべき優位

これ以外は移植であり、優位ではない。ここを見失うと「同じものを別の言語で書き直しただけ」に終わる。

| # | 優位 | 位置づけ | 対応する要件 |
|---|---|---|---|
| **A-3** | **unitypackage で配布されたモデルを、作者のシェーダのまま使える** | **主。Yuni の存在理由**（D-6） | F-18 |
| A-1 | 衣装が脚・体と衝突し、座っても貫通しない | 主。**クロスは Yuni が構成する**（D-10） | F-17 |
| A-2 | 座る・手を振るなど、ボーン回転の近似では作れない動作を再生できる | 主 | F-16 |

**この 3 つだけである。** 増やさないこと。優位でないものを優位のように扱うと、移植でしかない作業に「Yuni にしかできないこと」という名前がつき、判断を誤る。

**A-3 から「作者のクロスのまま」を外した（D-10、[ADR-0005](adr/0005-yuni-always-builds-cloth.md)）。** unitypackage 配布モデルのクロスは方式が統一されておらず（MagicaCloth v1 / v2 / VRChat PhysBone / DynamicBone / 無し）、**作者が使ったランタイムを Yuni が全部積むことはできない。** v1 は入手不可、PhysBone は VRChat SDK 依存で外部利用できない。方式ごとに変換器を足していく道は、moca が PMX で撤退した構造と同じである。

**シェーダは成立する。** lilToon での描画を PoC-2 で実証済み。**クロスだけを Yuni が構成する。**

**VRM 経路も同じ構成処理を使う（D-10）。** 違うのは手がかりの取得元だけであり、実装は共通になる。ADR-0004 で「おまけ」に降格させたが、**主経路の実装そのものになった。** ただし **1.0 の達成条件は VRM を含めない**（VRM の本命は moca であるため。D-6）。

### 1.3 スコープ外

- **PMX 対応。** moca は 0.7 で PMX を 1.0 の条件から外した（「統一規格が無く、達成できる見込みが無い」）。Unity 側の PMX ランタイムローダは個人製の小規模ライブラリしか存在せず、three.js の `MMDLoader` より状況が悪い。**Yuni では最初から対応しない**
- **`.unitypackage` そのもののランタイム読込。** 形式上不可能である。1.3.1 節
- **独自のモデル形式・独自コンテナの定義（D-4）。** 1.3.1 節
- **モデルファイルの同梱・再配布**（moca 4.4 を継承）
- **Windows 以外の OS。** UniWindowController は macOS に対応するが、資格情報保管とマスコット挙動の検証範囲を広げない
- **ボーンを持たない衣装の貫通（P-3）。** 1.0 の条件に含めない。`feasibility.md` R-1

#### 1.3.1 unitypackage 配布モデルへの対応方針（D-4）

**対応する。ただし独自形式は作らない。** この 2 つは両立する。

##### どうやっても消えない制約

**`.unitypackage` をランタイムに読むことはできない。** unitypackage は Unity Editor 向けのアーカイブ形式であり、その中のマテリアルや prefab はエディタでのインポート処理を経てはじめて意味を持つ。Unity アプリにしても読めるようにはならない。

したがって **モデルごとに一度 Unity Editor を通す工程は、どの設計でも消せない。** 「ファイルを D&D するだけ」は原理的に不可能である。設計で選べるのは*その工程の出力を何にするか*だけであり、選択肢は 2 つしかない。

| 出力 | 保たれるもの | 失われるもの | 独自形式 |
|---|---|---|---|
| **VRM**（UniVRM で変換） | 標準形式で完結 | 作者のシェーダ表現、標準外のリグ構造 | 不要 |
| **AssetBundle**（採用） | シェーダ・マテリアル・クロス設定・リグ構造がそのまま | — | **Unity 標準形式のため不要** |

##### AssetBundle を採る（D-4）

**AssetBundle は Unity の標準形式であり、こちらが定義するものではない。** 「独自規格を増やさない」という制約は、AssetBundle を使うことでは破られない。破るのは*その上に自作のコンテナをかぶせること*である。

本書 0.2 版は AssetBundle を ZIP でくるみ `manifest.json` を添えた `.yuni` を定義していた。**これは不要だった。** 理由は次のとおり。

`.yuni` の存在理由は「バンドルを開く前に互換性を判定したい」ことだけだった。しかし **AssetBundle のファイルヘッダには、`UnityFS` シグネチャとエンジンバージョン文字列が平文で先頭に入っている。** ヘッダを読むだけで判定できる。ZIP もマニフェストも要らない。

したがって Yuni が読むのは **素の Unity AssetBundle** である。拡張子は `.assetbundle` とする。

```
unitypackage 配布モデル
   │
   │  Yuni Packager（Unity Editor 拡張・本体リポジトリに同梱）
   │  利用者が一度だけ実行する
   ▼
 model.assetbundle        ← 素の Unity AssetBundle。独自形式ではない
   │
   │  Yuni がヘッダで互換性を判定 → ロード → 実体化
   ▼
 作者のシェーダ・クロス設定がそのまま生きる
```

##### 払うコストを承知しておく

AssetBundle を採る以上、次は避けられない。**これは `.yuni` をやめても消えない。形式の問題ではなく、AssetBundle という仕組みに内在するものだからである。**

- **Packager とランタイムで Unity バージョンをロックする。** AssetBundle は Unity バージョンに依存する
- **許可コンポーネントのホワイトリストを保守する。** AssetBundle にコードは入らないため、プレイヤー側に無いコンポーネントは Missing Script になる（F-18-4）
- **信頼できない入力を 1 つ抱える**（4.3 節）
- **Editor 拡張という第二の成果物を保守する**

**ホワイトリストの保守が moca の PMX と同じ轍にならないよう注意すること。** moca は PMX を「モデルごとの手当てが際限なく必要になる」（ADR-0015 / R-12）として実用から外した。同じ壊れ方をする形は「特定のモデルを通すためにホワイトリストへ例外を足す」である。**版を上げる形でのみ緩める**（F-18-4）。

##### VRM 経路も残す

AssetBundle を用意できない・したくない利用者のために、**UniVRM で VRM へ変換する経路も案内する**（ADR-0017 と同じ案内）。この経路ではシェーダ表現と作者のクロス設定が失われるが、**クロスについては F-17 が実行時に付け直すため実害が小さい。** 失われるのはシェーダ表現だけになる。

**どちらの経路でも A-1（座っても貫通しない）は成立する。** F-17 が両方を支えている。

### 1.4 想定利用者

moca の想定利用者を継承する。加えて **Yuni の主経路（F-18）では Unity Editor を自分で操作できることを前提とする**（D-6）。1.3.1 節のとおり、この工程は原理的に省けない。

**これは moca より狭い利用者層である。** 承知のうえで狭める。Unity を触りたくない利用者には moca を案内すればよく、そのために moca を残す（D-7）。

## 2. 用語定義

moca の第 2 章を継承する。以下を追加する。

| 用語 | 定義 |
|---|---|
| エモート | 座る・手を振るなど、あらかじめ用意されたモーションクリップによる全身動作。moca の F-14「体の動き」（手続き的な姿勢変化）とは別物であり、上位のレイヤで再生する |
| クロス | 衣装メッシュに対する物理シミュレーション。SpringBone と違い、コライダから押し戻される力を持つ |
| BoneCloth | ボーンを揺らす形式のクロス。スカート等、揺れ物ボーンを持つ衣装が対象 |
| MeshCloth | メッシュの頂点を直接動かす形式のクロス。ボーンを持たない衣装が対象 |
| クロスバックエンド | クロスシミュレーションの実装を差し替えるための抽象。**既定は SPCR JointDynamics**（MIT・同梱）。MagicaCloth2 は対応予定。最終退避は Null 実装（[ADR-0003](adr/0003-spcr-as-default-cloth-backend.md)） |
| クロス中間表現 | 「チェーンのルートボーン群」と「コライダの形状・配置」からなる**ソルバ非依存**の構造。VRM SpringBone 定義も、v1 プレハブから読み出した構成も、いったんこれへ落としてからバックエンドへ渡す |
| モデルバンドル | unitypackage 配布モデルを Yuni Packager で焼いた **Unity AssetBundle**。拡張子は `.assetbundle`。**独自形式ではない** |
| Yuni Packager | Yuni 本体リポジトリに同梱する Unity Editor 拡張。モデルバンドルとモーションバンドルを焼く |
| モーションバンドル | 利用者のモーション（`.anim` 等）を焼いた **Unity AssetBundle**。**モデル非依存**であり、一度焼けば任意のモデルで使える |

## 3. 機能要件

### 3.1 moca から継承するもの（変更なし）

以下は moca の同番号の要件をそのまま満たす。本書では再掲しない。

| 要件 | 内容 |
|---|---|
| F-05 | チャット |
| F-06 | LLM プロバイダ設定（OpenAI 互換 / Anthropic / Gemini の 3 アダプタ） |
| F-07 | 感情タグ解析と表情反映 |
| F-08 | 疑似リップシンク |
| F-09 | キャラクタープロファイル |
| F-10 | 会話履歴の永続化とコンテキスト管理 |
| F-12 | 音声での読み上げ（VOICEVOX / shirataki） |
| F-14 | 体の動き（感情に応じた姿勢、待機中の揺れ） |
| F-15 | 身振りタグ |

**移植であって再設計ではない。** 仕様に疑問が出た場合、moca 側の文書と実装を正とすること。改善したくなっても 1.0 までは我慢する。二つの製品が別々の挙動をすると、移行時に何が壊れたのか分からなくなる。

### 3.2 moca から継承するが変更があるもの

#### F-01 モデルの読み込み（変更）

- F-01-1〜F-01-6 は継承する
- **F-01-7（PMX 実験的対応）を削除する。** 1.3 節の理由による。`.pmx` を渡された場合は非対応である旨を明示して断ること
- **F-01-8（新規）** モデルバンドル（`.assetbundle`）を読み込めること。詳細は F-18
- **F-01-9（新規）** `.unitypackage` を直接渡された場合、**ランタイムには読めない旨と、Yuni Packager を通す手順**を提示すること（1.3.1 節）。黙って無視しないこと

**読み込める形式は `.vrm` と `.assetbundle` の 2 つである。** 増やさないこと。

#### F-02 モデル非表示・未設定モード（変更）

- F-02-1、F-02-2、F-02-4 は継承する
- **F-02-3 を緩和する。** moca は「レンダリングループを停止し、GPU および CPU を消費しないこと」と定めるが、Unity のプレイヤーループは停止できない。**代わりに次を要件とする**
  - モデルの更新・クロスの計算・カメラの描画を停止すること
  - `Application.targetFrameRate` を下げ、`OnDemandRendering` により描画呼び出しを間引くこと
  - **非表示時の CPU 使用率が、表示時に対して有意に低いこと**（実測値は 4.2 節で定める）

#### F-04 アイドル挙動（変更）

- F-04-1〜F-04-4、F-04-6 は継承する
- **F-04-5（SpringBone による揺れ）を置き換える。** Yuni では揺れ物も F-17 のクロスバックエンドが担う。クロスバックエンドが Null の場合に限り、UniVRM の SpringBone 実装へ退避すること

#### F-11 API キーの安全な保管（変更）

- F-11-1、F-11-2、F-11-4 は継承する
- **F-11-3（API キーを WebView 側へ渡さない）を削除する。** Yuni は単一プロセス・単一言語であり、プロセス境界が存在しない。この要件は成立しない
- **代替として F-11-5 を置く。** API キーは必要な瞬間にのみ資格情報マネージャーから取得し、フィールドやシーンオブジェクトへ保持しないこと。取得した値は使用後に破棄すること

**これは実質的な後退である。** moca では IPC 境界が構造的な防壁だったが、Yuni ではその防壁が無い。規約でしか守れなくなる。既知の後退として記録する。

#### F-13 デスクトップマスコット表示（変更）

- F-13-1〜F-13-10 の**要求はすべて継承する。** とくに「操作できないウィンドウを作ってはならない」という moca の原則、および F-13-1 / F-13-9 / F-13-10 による多重の入口封鎖をそのまま守ること
- **実装手段が変わる。** Tauri のウィンドウ設定ではなく [UniWindowController](https://github.com/kirurobo/UniWindowController) を用いる
- **moca ADR-0016（透過は生成時にしか決められない）の制約は Yuni には無い。** UniWindowController は実行時に透過を切り替えられる。したがって「常に透過で生成し通常表示では body を不透明に塗る」という moca の回避策は不要
- **moca の「別ウィンドウにはしない」判断（WebView ごと分かれ状態ストアが割れる）も Yuni には当てはまらない。** ただし**同一ウィンドウ内の吹き出しという設計は維持する**（F-13-8）。理由が消えても、体験としてはこちらが正しい
- **F-13-4（外接矩形まで窓を詰める）は自作が要る。** モデルのワールド境界をカメラ空間へ射影して画面上の矩形を求め、ウィンドウを合わせる

### 3.3 Yuni で新設するもの

#### F-16 エモート

moca の F-14（手続き的な姿勢）・F-15（身振りタグ）とは別の層である。両者は共存し、干渉しない。

> **段階（D-2）**: 0.1 で**実験的機能**として載せ、0.7 で F-14 の姿勢レイヤと合流させて正式化する。実験的機能の扱いは 10.1 節。

- **F-16-1** モーションクリップによる全身動作を再生できること。少なくとも「座る」を含むこと
- **F-16-2** エモートは Humanoid リターゲティングにより、体格の異なるモデルでも動作すること
- **F-16-3** エモートは F-14 の姿勢・呼吸・F-04 のアイドル挙動の**上位レイヤ**として合成されること。エモート中も呼吸とまばたきは止まらないこと
- **F-16-4** エモートの開始・終了は補間すること。突然ポーズが切り替わらないこと
- **F-16-5** エモートには**接地基準**を持たせること。マスコット表示には床が無いため、腰の高さと足首の目標位置をモデルの身長で正規化して保持し、モデルが宙に浮いたり床にめり込んだりしないこと
- **F-16-6** エモートは会話から独立して手動でも実行できること。将来のタグ駆動（`[sit]` など）は F-15 のパーサ拡張に乗せる
- **F-16-7【改訂】エモートのモーションは「同梱分」と「利用者の持ち込み分」の 2 経路を持つこと**
  - **F-16-7-a** 最小限のエモートを同梱すること。**同梱分は再配布可能なライセンスのものに限る**（NF-L-4）。利用者が何も用意しなくても座れる状態にする
  - **F-16-7-b** **利用者が自分のモーションを持ち込めること。** `.anim` は Unity のアセット形式でありランタイムに直接読めないため、**AssetBundle 経由とする**（F-18 と同じ仕組み。独自形式を作らない = D-4）
  - **F-16-7-c** モーションバンドルは**モデルバンドルとは別に持てること。** モーションは Humanoid リターゲティングによりモデル非依存であり、一度作れば任意のモデルで使える
  - **F-16-7-d 【重要】利用者のモーションを Yuni が再配布しないこと。** 有償・再配布不可のモーションが持ち込まれることを前提に設計する。バンドルは利用者のローカルに置き、パス参照のみを保持する（モデルと同じ扱い。NF-L-5 の姿勢）

  > **0.5 版までは「同梱するもののみ」としていた。** これは moca の判断（「VRMA や VMD は同梱できず利用者負担になるため手続き的に生成する」）を引き写したものだったが、**Yuni では利用者が Unity Editor を使う前提がある**（1.4 節）。持ち込みの敷居が moca より低い。

- **F-16-9** 持ち込んだモーションが Humanoid でリターゲットできない場合、その旨を提示すること。黙って再生しないこと
- **F-16-8** エモート中にモデルを差し替えた場合、および読み込みに失敗した場合、エモートは中断して既定姿勢へ戻ること

#### F-17 クロスシミュレーション

**Yuni の存在理由である。**

> **段階（D-2）**: 0.1 で**実験的機能**として載せ、0.7 で正式化する。実験的機能の扱いは 10.1 節。**0.1 の目的は完成度ではなく、A-1 が成立することを実機で示すことである。**

> **クロスは常に Yuni が構成する（D-10、[ADR-0005](adr/0005-yuni-always-builds-cloth.md)）。**
> 作者のクロス設定は「移植対象」ではなく「手がかり」である。読めれば精度が上がり、読めなくても構成できること。
>
> **必要なのは「衣装のボーンがあること」だけである。** 作者がどの方式（MagicaCloth v1 / v2 / PhysBone / DynamicBone / 無し）を使っていても同じ処理で扱う。
>
> | 経路 | 手がかりの取得元 | 構成する場所 |
> |---|---|---|
> | モデルバンドル（主） | プレハブ内の既存設定（読めれば） | Unity Editor（Packager）。**実行時構築を要しない** |
> | VRM | SpringBone 定義 | 実行時 |
> | 手がかりが無い | Humanoid とボーン構造から推測（F-17-4） | 同上 |

- **F-17-1** モデルに対し、**利用者の操作なしに**クロスを構成すること。手がかりの有無に関わらず構成を試みること
- **F-17-2** VRM の SpringBone 定義（チェーンおよびコライダ）を読み出し、BoneCloth へ変換すること
- **F-17-3** Humanoid ボーン構造から、腰・尻・太もも・上腕にカプセルコライダを手続き生成すること。寸法はボーン間距離から求め、身長で正規化すること。**座り姿勢での貫通に対する主たる対処はこれである**
- **F-17-4** SpringBone 定義を持たないモデルでは、ボーン名からの推測により構成を試みること。推測に失敗した場合はクロス無しで表示を成立させ、その旨を診断パネルへ出すこと。**黙って何もしないことは許さない**
- **F-17-5【改訂】作者のクロス設定は「手がかり」として使うこと（D-10）。** そのまま移植しようとしないこと。読み取るべきは次の 3 つに限る
  - **どのボーンが衣装か**（チェーンのルート群）
  - **どのコライダに当てるか** — 実モデルの調査では、Chifuyu のスカートは太もも 2 本のみ、Karin は Hips + 太もも 2 本を指定していた。**作者が意図した当て先であり、ゼロから推測するより確実**
  - **粒子半径や重力の目安**
  
  ソルバ固有の詰め値（質量カーブ、減衰、拘束の強さ）は読まないこと。**移し先で意味が変わるため、読んでも判断を誤らせるだけである**
- **F-17-6** クロスの実装は `IClothBackend` として抽象化すること。実装は次の 3 つとする（[ADR-0003](adr/0003-spcr-as-default-cloth-backend.md)）
  - `SpcrClothBackend` — **既定。1.0 の実装対象。** [SPCR JointDynamics](https://github.com/SPARK-inc/SPCRJointDynamics)（MIT）。**リポジトリに同梱する**
  - `MagicaClothBackend` — **対応予定。インターフェースのみ確定させ、実装は 1.0 の条件に含めない。** 所持者が有効化する
  - `NullClothBackend` — 最終退避。UniVRM の SpringBone へ委譲する
- **F-17-7 【重要】有償アセットを 1 つも所持しない状態で、リポジトリを clone してビルドが通り、かつクロスが動くこと。** 既定が MIT の SPCR であるためこれが成立する。**CI でこの状態のビルドとクロスの経路を常時検証すること**。理由は 4.4 節
- **F-17-8** クロスの有効・無効を設定から切り替えられること。F-04-6 と同じ扱いとする
- **F-17-9** クロスの構築は非同期であり数フレームを要する。構築中もアプリが応答すること。構築完了までは SpringBone または静止で表示を成立させること
- **F-17-10** ボーンを持たない衣装（頂点駆動が要るもの）は 1.0 の条件に含めない。**SPCR に MeshCloth 相当は存在しない**（ADR-0003）

  > **D-10 によりこの制約の重みが下がった。** 従来は「作者が MeshCloth を使っていると変換できない」ことが問題だったが、**常に Yuni が BoneCloth で構成するため、作者の方式は関係なくなった。** 衣装にボーンさえあれば構成できる。真に問題になるのは**ボーンが 1 本も無い衣装**だけであり、これは元から 1.0 の条件外である
- **F-17-11【抽象の切り方】** `IClothBackend` は **BoneCloth 相当（ボーン駆動）だけを表現すること。** MeshCloth を同じインターフェースへ混ぜないこと。SPCR に存在しない概念であり、混ぜると実装が 1 つしかない段階で抽象を誤る
- **F-17-12** バックエンドは**能力照会**を持つこと。呼び出し側が「このバックエンドは何ができるか」を問える形とし、`if (backend is ...)` のような型分岐を書かせないこと
- **F-17-13** バックエンドへの入力は**クロス中間表現**（2 章）とすること。VRM SpringBone 定義も、モデルバンドルが持ち込む既存のクロス設定も、いったん中間表現へ落としてから渡すこと。**ソルバ固有の値を中間表現へ持ち込まないこと**

#### F-18 モデルバンドル（unitypackage 配布モデルの持ち込み）

**A-3 を担う。** 方針と、独自形式を採らない理由は 1.3.1 節。

**Packager（焼く側）** — F-18-1〜7 / 13 / 14

> 番号は追記順である。**要件 ID は振り直さない。** F-18-13 / 14 は後から実測で判明した Packager 側の要件であり、位置はここが正しい。

- **F-18-1** Yuni Packager（Unity Editor 拡張）を本体リポジトリに同梱すること
- **F-18-2** Packager は利用者の Unity プロジェクト上で、モデルの prefab から **素の Unity AssetBundle** を出力すること。**独自のコンテナでくるまないこと**（D-4）
- **F-18-3** 出力にはメッシュ・マテリアル・シェーダ・アニメーション・クロス設定を含めること
- **F-18-4** Packager は**許可コンポーネントのホワイトリスト検証**を行うこと。ホワイトリスト外の MonoBehaviour は剥がし、剥がしたものを一覧で提示すること。理由は次の 2 つ
  - AssetBundle にコードは入らないため、プレイヤー側に無いコンポーネントは Missing Script になる（構造的な制約）
  - 任意の AssetBundle を読むことは攻撃面である（4.3 節）
  - **ホワイトリストは版を持ち、緩めるときは版を上げること。個別のモデルを通すために例外を足さないこと。** ここが moca の PMX と同じ壊れ方をする箇所である（1.3.1 節）
- **F-18-5** Packager は出力前に**プレビューを提示すること。** 焼いてから壊れているのに気づくのでは遅い。少なくとも次を見せること
  - 剥がしたコンポーネント
  - 解決できなかったシェーダ、**および移行が未完了のマテリアル**（F-18-14）
  - Humanoid ボーンの欠落
  - **クロス設定の変換結果**（変換できたチェーン数・コライダ数と、**移せなかった設定の一覧**）（F-18-7）
- **F-18-6** Packager とランタイムの Unity バージョンは同一とし、CI で固定すること
- **F-18-7【改訂】クロス設定の読み取り（変換ではない）** モデルが既存のクロス設定（MagicaCloth v1 / v2 / PhysBone / DynamicBone 等）を持つ場合、Packager は**クロス中間表現へ読み出して手がかりとして使うこと**（D-10、F-17-5）。**そのまま移植しようとしないこと。** 読み取れなくてもボーン構造から構成すること。元のコンポーネントは剥がすこと（プレイヤー側に存在しないため Missing Script になる）
  - **v1 のアセットを所持していなくても変換できる。** プレハブの YAML を直接読めば、チェーンのルートボーン群とコライダの形状・配置は取り出せる（[ADR-0003](adr/0003-spcr-as-default-cloth-backend.md) に実測例）
  - **ソルバ固有の詰め値（質量カーブ等）は移らない。** 移せなかった項目を F-18-5 のプレビューで提示すること。**黙って落とさないこと**
  - したがって **F-18-4 のホワイトリストに v1 / v2 のコンポーネントは入らない。** それらは「変換対象」であって「許可対象」ではない

  **【実測で判明した構造上の制約（2026-08-31、Tokyo6 Chifuyu）】**

  - **クロス設定は 1 箇所にまとまっていない。** 揺れ物の定義とコライダは別の場所にある。**`Magica_root` だけを見ても変換できない**

    | 探すもの | 場所 |
    |---|---|
    | 揺れ物のチェーン定義 | `Magica_root` 直下（`Magica Bone Cloth_*`） |
    | **コライダの形状・配置** | **ボーン階層の中に散在**（`Chest` / `Head` / `LegD_L` / `LegD_R` の子） |
    | 両者の対応づけ | チェーン側の `teamData.colliderList` |

    コライダがボーン階層にあるのは**正しい設計である。** 体に追従しなければ、脚を動かした瞬間に置いていかれる。変換後も**同じボーンの子として配置すること**

  - **`colliderList` は fileID による参照である。** 変換器は **fileID からオブジェクトを解決する処理**を持つこと。名前で引き当てないこと（同名オブジェクトが存在しうる）

- **F-18-13【FBX ごと焼くこと】** モデルのプレハブは **FBX のプレハブインスタンス**であり、ボーンの実体は FBX 側にある（Chifuyu では stripped Transform が 111 個）。**プレハブだけを焼くと壊れる。** 依存を辿って FBX を含めること

- **F-18-14【シェーダの移行を焼く前に完了させること】** 配布モデルのマテリアルは古い版のシェーダで作られていることがある。Tokyo6 では取り込み時に lilToon の移行処理が 8 枚に対して走った。**移行前に焼くと古い形式のまま固まる。** F-18-5 のプレビューで移行状況を提示すること

**ランタイム（読む側）** — F-18-8〜12

- **F-18-8** ランタイムは **AssetBundle をロードする前にファイルヘッダを読んで**互換性を判定すること。AssetBundle は先頭に `UnityFS` シグネチャとエンジンバージョン文字列を平文で持つ。**この性質があるため独自コンテナは要らない**（1.3.1 節）
- **F-18-9** 判定に失敗した場合はロードせず、**どの項目が合わないかを提示して断ること。** 静かに壊れてはならない。判定項目は次のとおり
  - シグネチャが `UnityFS` であること
  - エンジンバージョンがプレイヤーと一致すること
  - ロード後、必要なコンポーネントが Missing Script になっていないこと（MagicaCloth2 未搭載ビルドで、クロス設定済みバンドルを読んだ場合がこれに当たる）
- **F-18-10** バンドル内にモデルの素性を記した ScriptableObject を含め、ランタイムはこれを読んで診断へ渡すこと（F-19）。Humanoid ボーンの欠落、剥がされたコンポーネント、身長、表情名、クロス設定の有無を含めること
- **F-18-11** モデル作者の利用規約をバンドルへ含められること。含まれている場合、Yuni はモデル読み込み時にその存在を提示すること（moca 4.4 の姿勢を継承）
- **F-18-12** 読み込みに失敗してもアプリを終了しないこと。**信頼できない入力として扱うこと**（4.3 節）

#### F-19 モデル互換性診断

moca の診断パネル（0.1 で実装）を拡張する。**「動かない理由が分からない」が最も困る**という moca の姿勢を継承する。

- **F-19-1** 読み込んだモデルについて、次を診断パネルへ提示すること
  - Humanoid ボーンの充足状況（エモートの成否を決める）
  - SpringBone 定義の有無とチェーン数
  - クロスの構成結果（自動生成できたか、推測で構成したか、構成できなかったか）
  - 生成した人体コライダの数
  - 表情の数、テクスチャの数（moca R-10 を継承）
- **F-19-2** クロスが構成できなかったモデルについて、その理由を提示すること

## 4. 非機能要件

moca の第 4 章を基礎とし、以下の差分を持つ。

### 4.1 動作環境

| 項目 | moca | Yuni |
|---|---|---|
| OS | Windows 10 1809 以降 / 11、x64 | 継承 |
| 必須ランタイム | WebView2 Runtime | **不要** |
| GPU | WebGL 2.0 | **DirectX 11 以上** |
| 配布形態 | MSI / NSIS インストーラ | 継承。WebView2 ブートストラッパは不要になる |
| ビルド | — | **IL2CPP 必須**（4.4 節） |
| Unity | — | Unity 6（LTS）。バージョンは固定し CI で縛る |

### 4.2 性能

| 項目 | moca の目標 | Yuni の目標 | 理由 |
|---|---|---|---|
| 描画 | モデル 1 体で 60fps | 継承 | クロスの計算を含めて 60fps を維持すること |
| 起動 | 3 秒以内 | **5 秒以内** | Unity ランタイムの初期化が乗る |
| モデル読み込み | VRM 20〜60MB で 5 秒以内 | 継承。**クロス構築を含めて 8 秒以内** | F-17-9 により構築中も応答すること |
| 配布サイズ | 約 15MB | **300MB 以下** | 超える場合は Managed Stripping とテクスチャ圧縮で対処する |
| 3D ビュー非表示時 | GPU / CPU 使用をゼロ | **表示時の 20% 以下** | F-02-3。Unity では 0 にできない |

**この表は後退を含む。** 隠さず記録する。マスコットとして常駐する製品で起動時間と配布サイズが悪化することの意味は、0.6（マスコット表示）の時点で実機で評価すること。

### 4.3 セキュリティ

moca の 4.3 を継承する。ただし次が変わる。

- **Tauri capabilities に相当する仕組みが無い。** ファイルアクセスの制限はアプリの実装責任になる。読み込み対象を利用者が明示的に選択したファイルに限ること
- **PMX を落とすため、moca が例外としていた「ディレクトリまで許可を広げる」が不要になる。** VRM もモデルバンドルも 1 ファイルで完結する
- **モデルバンドルは信頼できない入力である。** F-18-4 のホワイトリスト検証（焼く側）と F-18-8 / F-18-9 のヘッダ判定（読む側）で二重に守ること。AssetBundle は新しいコードを実行しないが、既存コンポーネントの組み合わせと巨大なアセットによる異常終了は起こしうる。**読み込み失敗でアプリを落とさないこと**（F-18-12）
- テレメトリを送信しないこと（継承）
- 外部通信は利用者が設定した LLM および TTS のエンドポイントに限ること（継承）

### 4.4 ライセンスと権利

moca の 4.4 を継承する。加えて**同梱物の扱いを定める。**

### 依存物の扱い

| 依存物 | ライセンス | リポジトリへ | 配布ビルドへ |
|---|---|---|---|
| **SPCR JointDynamics** | MIT | ✅ **同梱する** | ✅ |
| **lilToon** | MIT | ✅ **同梱してよい**（LICENSE.txt を添える） | ✅ |
| **UniVRM** | MIT | ✅ | ✅ |
| **UniWindowController** | MIT | ✅ | ✅ |
| **MagicaCloth2** | Asset Store EULA | ❌ **禁止** | ✅ 許可（下記） |
| **MagicaCloth v1** | Asset Store EULA | ❌ | ❌ **採用しない**（[ADR-0003](adr/0003-spcr-as-default-cloth-backend.md)） |
| モデルファイル | 各作者 | ❌ | ❌ |

**例外的な扱いを要するのは MagicaCloth2 だけである**（D-5 により既定から外れたため、影響範囲が縮んだ）。

| MagicaCloth2 について | 可否 | 対処 |
|---|---|---|
| リポジトリへのコミット | **禁止** | `.gitignore` に入れる |
| `.unitypackage` の再配布 | **禁止** | しない |
| 配布ビルドへの組み込み | **許可** | Asset Store EULA は "incorporated and embedded components" として許可している |

- **NF-L-1** MagicaCloth2 をリポジトリへコミットしないこと
- **NF-L-2 【強化】有償アセットを 1 つも所持しない者がリポジトリを clone してビルドでき、かつクロスが動くこと。** 既定バックエンドが MIT の SPCR であるため成立する（D-5）。**CI ではビルドの成否だけでなく、クロスの経路が生きていることまで検証すること。** 従来は `NullClothBackend` への退避を許していたが、それでは「Yuni の存在理由が動いていない Yuni」しか検証できない
- **NF-L-3** **MagicaCloth2 を組み込んだ配布ビルドは IL2CPP とすること。** Mono ビルドは `Managed/MagicaCloth2.dll` をそのまま配置し、EULA が禁じる「抽出可能な形」に該当しうる。**MagicaCloth2 を含まないビルドにこの制約は無い**（ただし性能上の理由で IL2CPP を推奨する）
- **NF-L-4** **同梱する**エモートのモーションデータ、シェーダは再配布可能なライセンスのものに限ること
- **NF-L-7** **利用者が持ち込んだモーションを Yuni が再配布しないこと**（F-16-7-d）。有償・再配布不可のものが持ち込まれる前提で設計する。バンドルは利用者のローカルに置き、パス参照のみを保持する
- **NF-L-5** モデルファイルは一切同梱しないこと（継承）
- **NF-L-6** MIT の依存物を同梱する際は、それぞれの LICENSE ファイルを配布物へ含めること

### 4.5 国際化 / 4.6 保守性

moca の 4.5 / 4.6 を継承する。4.6 について Yuni では次の形を取る。

- ロジック層を **`UnityEngine` に依存しない Assembly Definition** へ隔離し、EditMode テストの対象とする
- カバレッジ目標 80%（継承）
- 拡張ポイントは moca の 3 点（モデル形式・LLM プロバイダ・音声合成）に **クロスバックエンド**を加えた 4 点とする

## 9. リスクと軽減策

`feasibility.md` 第 6 章の R-1〜R-11 を参照する。本書では再掲しない。

### 9.1 二重管理という意図的なコスト（D-7）

`feasibility.md` の R-8 は「moca と Yuni の二重管理が長引く」を**回避すべきリスク**として扱い、軽減策を「moca は後継が 1.0 に達した時点で保守終了と宣言する」としていた。

**[ADR-0004](adr/0004-unitypackage-first-coexist-with-moca.md) によりこれを撤回した。二重管理は回避すべきリスクではなく、意図して選んだコストである。**

払い続けるもの:

- 感情タグパーサ、各モーションコントローラ、カナ→ビセーム写像を **TypeScript と C# の二重で保守する**
- LLM 3 アダプタを **Rust と C# の二重で保守する。** プロバイダの仕様変更があれば両方を直す
- `emotion-protocol.md` の変更は両方へ波及する

**唯一の防波堤は「仕様の正を moca 側に置き続けること」である**（0 章）。Yuni 側で仕様を先に変えた瞬間、二製品の挙動が割れ、どちらが正しいのか誰にも分からなくなる。

### 9.2 moca から引き継ぐリスク

moca のリスク表のうち、Yuni で**消えるもの**と**残るもの**を記録する。

| moca のリスク | Yuni での状態 |
|---|---|
| R-1（MMDLoader の API 不安定 / ammo.js） | **消滅。** PMX を落とす |
| R-3（WebView2 の WebGL 性能） | **消滅。** WebView2 を使わない |
| R-6 / R-7 / R-12（PMX のモーフ名・利用規約・保守） | **消滅。** PMX を落とす |
| R-2（小規模モデルが感情タグを無視する） | 残る |
| R-4（大容量モデルによるメモリ消費） | 残る。モデルバンドルにより増大しうる |
| R-5（shirataki の外部依存） | 残る |
| R-8（プロバイダ API の仕様変更） | 残る。**二重管理により影響が倍になる。** moca 側と Yuni 側の両方を直すことになる（D-7） |
| R-9（推論モデルが本文を返さない） | 残る |
| R-10 / R-11（失敗が何も出ずに起きる） | 残る。F-19 で拡張する |

| U-10 | MeshCloth（P-3）を追うかどうか | **未決。** 1.0 の条件からは外している。**SPCR に MeshCloth 相当は無いため、追うなら `MagicaClothBackend` の実装が前提になる**（D-5）。1.0 到達後に再判断する |
| U-11 | ホワイトリストの初版に何を入れるか | **未決。** 実モデルを通して足りないものを見つけ、**版を上げる形で**足す。個別モデルのための例外は足さない（F-18-4）。**この判断を緩めた時点で moca の PMX と同じ道に入る** |
| U-12 | バンドル経路と VRM 経路の使い分けをどう案内するか | **未決。** 両方を残す（1.3.1 節）以上、利用者はどちらを選ぶか判断できる必要がある。0.3 着手時に案内文を定める |
| U-13 | レンダーパイプライン（Built-in RP / URP） | **未決。着手前に決めること。後から変えると全マテリアルに波及する。** **VRM 0.x には URP 対応の MToon が存在しない**（URP 対応は VRM 1.0 のみ）。URP を選ぶと F-01-3（VRM 0.x / 1.0 の両対応）と衝突する。一方 UniWinC_VRM は URP を採っており、透過ウィンドウとの組み合わせの実績はそちら側にある。**lilToon は Built-in / URP / HDRP すべてに対応するため、モデルバンドル経路（F-18）はどちらでも成立する。制約になるのは VRM 経路だけである。** **PoC-1 の後に ADR で決める。** PoC-1 自体は変数を減らすため Built-in RP で行う（`poc/poc-1.md` 2 節） |
| U-14 | SPCR の保守停止をどう扱うか | **未決だが緊急度は下がった。** 2026-08-30 の実測で、Unity 6000.0.82f1 上で **v2.0.11 が無修正でコンパイル成功**（エラー 0 / 非推奨警告 4）。**現時点でフォークの必要は無い。** フォークに踏み切る基準は「SPCR 本体に手を入れざるを得なくなったとき」とする。その最初の候補は `package.json` の `com.unity.burst` 依存宣言漏れ（[ADR-0003](adr/0003-spcr-as-default-cloth-backend.md)） |
| U-15 | 二重管理をいつまで続けられるか | **未決。** D-7 で恒久共存を選んだが、**実際に払い続けられるかは実績でしか分からない。** moca 側に修正が入るたび Yuni へ写す作業が発生する。半年後に振り返り、片方の更新が止まっていないかを確認すること（9.1 節） |
| U-16 | moca 側の README に棲み分けを書くか | **未決。** 利用者が「どちらを使えばよいか」を判断できる必要がある。VRM なら moca、unitypackage なら Yuni。**両リポジトリの README に相互リンクと棲み分けを書くのが筋**だが、moca 側への変更になるため別途判断する |
